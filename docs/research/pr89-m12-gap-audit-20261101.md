## Why a zero internal gap does not settle this comparison

For minimization, an exact feasible incumbent P and valid global lower bound D
must satisfy D <= z* <= P. Gurobi reports the relative gap as
`abs(ObjVal-ObjBound)/abs(ObjVal)`. Here each run's own P and D coincide,
so its own reported gap is zero. The calculation does not compare its
incumbent with incumbents from another run.

If B's point were proved exactly feasible for the same integer model and G's
bound were proved valid in exact arithmetic, their ordering would be
impossible. At least one premise—exact feasibility, bound validity, model
identity or attribute interpretation—would have to fail. A0.01% termination
criterion can explain different epsilon-optimal incumbents in general;
it cannot, by itself, make an exact valid lower bound exceed an exact
feasible point. Gurobi's finite-precision gap is not an exact certificate.
See its [gap definition](https://docs.gurobi.com/projects/optimizer/en/current/reference/attributes/model.html#mipgap)
and [absolute feasibility and integrality tolerances](https://docs.gurobi.com/projects/optimizer/en/current/concepts/numericguide/tolerances_scaling.html).

The frozen [solver implementation](https://github.com/unb-lamfo-or-ai-hpc/cfl-gurobi-gnn/blob/9ab7823c6886d19e9ec865141a1cd35b3c3c16e5/scripts/evidence/pr86_solver.py)
reads `ObjVal`, `ObjBound` and `MIPGap` directly after its single optimize call.
The independent `common_gap` function computes the absolute relative
difference without rounding or clamping a nonzero difference to zero.
The exported terminal trajectory and summary agree. This weakens an
export-format explanation. It does not independently validate the solver's
bound. `ObjBoundC` and `Work` were not exported; they cannot now be recovered
as terminal model attributes from the disposed in-memory model. The closed
log may retain related observations, at its printed precision.

## The strongest current hypothesis: tolerance-sensitive incumbents

The received summaries show B3725/B3727 with maximum integrality residual
5.207335889e-8 and R3728 with5.207335932e-8. Their maximum row residuals
are about1.3e-11. All pass the original `IntFeasTol=1e-5` and
`FeasibilityTol=1e-6` checks. G3726 reports zero for both residuals. A
floating-point feasibility check with those tolerances does not establish
exact binary feasibility.

There is directly relevant prior evidence, rather than just a generic
numerical conjecture. The [historical M12 audit](https://github.com/unb-lamfo-or-ai-hpc/cfl-gurobi-gnn/blob/9ab7823c6886d19e9ec865141a1cd35b3c3c16e5/docs/research/pr86-m12-audit-final-nine.md)
checked six stored PR86 vectors of this same model SHA256. The two controls
each had one nonintegral integer value. Rounding integers only in memory,
leaving continuous values unchanged, created a row violation of0.0000416587,
about41.66 times the original row tolerance. Four G vectors were unchanged
by rounding and passed the floating-point checks. These are historical
vectors, not the newly received PR89 vectors.

The recorded historical coefficient range includes800. As a scale
illustration, 800 times5.20734e-8 is about4.16587e-5. A tiny binary deviation
can therefore matter to an original-unit row. This is consistent with the
[tolerance amplification described by Gurobi](https://support.gurobi.com/hc/en-us/articles/360012237872-Why-does-Gurobi-sometimes-return-non-integral-values-for-integer-variables).
The specific affected variable and linking row in the current jobs still
need to be located; equal maximum residuals do not prove equal vectors.

Two cautions prevent an overclaim. First, the old rounding objective changes
were only about3.15e-8 and1.54e-7, much smaller than today's4.50e-4
cross-run difference. A direct rounding-cost calculation alone is therefore
not a sufficient explanation. Second, failure of the integer-rounded copy
does not prove that the integer assignment has no feasible continuous
completion, or that every genuinely feasible solution costs more than G's.
Finding such a completion would require a separate optimization, outside
this read-only audit. Nor do zero observed residuals establish an exact
optimality certificate for G. M4 has its own broader rounding limitation;
it must not inherit M12's more favorable G diagnostics.

## Does the warm start trap the tree in a local optimum?

That is not the mechanism implemented in this campaign. The
[native adapter](https://github.com/unb-lamfo-or-ai-hpc/cfl-gurobi-gnn/blob/9ab7823c6886d19e9ec865141a1cd35b3c3c16e5/src/cfl_gnn/solvers/neural_guidance.py)
uses the `partial_mip_start` branch and sets `Start`; it does not use the
separate fixing or local-branching branches. The executor checks the
mathematical signature before/after applying starts and verifies that
unselected starts are undefined. Both R and G supply20000 binary starts
out of1156800 binary variables, with different assignment hashes. The
remaining variables remain available to global branch-and-bound.

A partial start supplies a candidate for completion, as described in
[Gurobi's Start attribute](https://docs.gurobi.com/projects/optimizer/en/current/reference/attributes/variable.html#start).
It may change incumbents, cuts, branching and the amount of work needed to
close the bound. It is not a restriction to a neighborhood. The root LP
relaxation is a lower-bounding problem, not the final incumbent, and its
value must not be confused with R's predicted partial start. Under exact
arithmetic a poor start does not justify certifying a worse local solution
as the global optimum. Numerical tolerances and trajectory-dependent
processing remain plausible explanations requiring evidence.
